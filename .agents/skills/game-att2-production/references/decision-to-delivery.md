# Decision to delivery

Use for D0 planning and backlog updates. Current design belongs in the five living
documents. The execution plan is a coordination contract, not a sixth design source.

## Decision tree and interview

Read the local `grill-me` skill when interviewing. Look up facts first; ask the owner
only about genuine preference, identity, risk acceptance, or unresolved experience.
Distinguish:
- **Already decided:** cite the current owner passage; do not re-interview.
- **Technical choice:** reversible and experience-neutral; record and proceed.
- **Fixture hypothesis:** exact candidate plus test/revision rule; owner selects it.
- **Owner choice:** alternatives, recommendation, consequence, and blocked tickets.
- **Downstream:** explicitly outside this gate with its reactivation trigger.

A decision record has ID, question, status, authority, options, recommendation/rationale,
owner, prerequisite IDs, affected tickets, selected answer/date, and reopen trigger.
No answer or elapsed time is not approval. Ask a small independent frontier, not
questions whose answers depend on one another. Record only actual answers.
Recommendations may be creative but must be labelled proposals.

## Paper closure

D0 is closed only when the living ledger's required items are decided or explicitly
excluded by the owner, numeric fixture rules have exact semantics and acceptance cases,
and each minimum demo capability has a testable path. Final fun/balance cannot be
settled on paper; assign human evidence gates and revision criteria.

Check particularly: selected opening -> legal continuation; reward exclusivity ->
meaningful Blood/graft routes; acquisition -> later test; included progression ->
natural award/use/persistence observation; boss novelty -> disclosed causal ending;
death-prevention ordering; Attention refresh and Evade -> no free cycle.
An accepted direction is not an exact event-order or numeric rule.

## Spec and ticket handoff

Use local `to-spec` for bounded acceptance synthesis and `to-tickets` for one file per
work item. Default to local Markdown in the package's existing planning surface;
external tracker synchronization requires an explicit target and publication request.
Never auto-label unresolved product work ready-for-agent.

Statuses: DRAFT, BLOCKED-OWNER, BLOCKED-DEPENDENCY, READY-PAPER, READY-IMPLEMENTATION,
IN-PROGRESS, VERIFIED, DEFERRED. READY-IMPLEMENTATION additionally requires the exact
runtime gate, resolved touched decisions, and predecessor evidence.

Each runtime slice owns one player-observable capability through input, domain mutation,
visible consequence, and test. Do not invent API/database layers for a desktop game.
A tool spike must test a named uncertainty. Do not equate a context-window size with
a calendar estimate. Estimate only after scope, tools, and actual development pace
are known; report uncertainty.

Include authority anchors and decision IDs; acceptance with positive/negative cases;
blocking tickets with causal reasons; evidence artifact requirements; out-of-scope
items; rollback/rework boundary. Keep blockers acyclic and semantic, not decorative.
Use conditional branches only for genuinely unresolved choices; do not reopen an
already selected fight count. Scope cuts require explicit owner decisions.

Changes to an approved decision update its living source, dated ledger entry,
dependent tickets, and acceptance cases together. Tickets never override rules.

For this D0 packet, run `scripts/validate_planning.py --root <workspace>` from the
production skill folder with an available Python. It checks the current packet's
simple skill metadata, local file links, decision/requirement coverage, ticket IDs,
blocked runtime statuses, and dependency cycles. It is not a general YAML parser,
semantic acceptance test, automatic skill-discovery test, or proof of gameplay.
